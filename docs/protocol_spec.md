# UART Protocol

The live ESP32/ESP8266 link uses printable ASCII packets with the following framing:

```text
<COMMAND|TOKEN|KEY=VALUE>
```

`<` starts a packet and `>` ends it. CR/LF characters are ignored while assembling a packet, so both sides may use `println`. Payload bytes must be printable ASCII (`0x20`–`0x7e`). The configured maximum payload is 128 bytes and the maximum token count is 12. There is no CRC or XOR checksum in the current implementation.

## Transport

- ESP32: `Serial2`, RX GPIO16, TX GPIO17, 115200 baud, 8N1.
- ESP8266: `Serial`, GPIO3 RX and GPIO1 TX on the NodeMCU board, 115200 baud.
- The wiring file requires a shared ground.
- Each loop processes at most 32 received serial bytes. The ESP8266 command queue holds eight packets and dispatches at most one command per loop.

## Controller-to-output packets

| Packet | Meaning |
| --- | --- |
| `<PING|SEQ=n>` | Liveness probe. `SEQ` is generated by the ESP32. |
| `<FULL_SYNC|SEQ=n|R1=0|R2=1|R3=0|R4=1>` | Authoritative relay snapshot. |
| `<SET_LED_STATE|SEQ=n|MODE=SOLID|BR=150|SPD=5|PWR=1|CR=30,0,20>` | Desired NeoPixel state and acknowledgment sequence. |

The live ESP32 link currently sends `PING`, `FULL_SYNC`, and `SET_LED_STATE`. `FULL_SYNC` contains relay fields only; LED state is sent separately because it has its own apply/ack/retry tracking.

The ESP8266 dispatcher also accepts these command forms, whether or not the current ESP32 application emits them directly:

```text
<HEARTBEAT>
<HB>
<SET_RELAY|1|ON>
<SET_RELAY|1|OFF>
<SET_COLOR|255|0|0>
<CLEAR_LEDS>
<SET_BRIGHTNESS|128>
<SET_EFFECT|RAINBOW>
<GET_LED_DIAG>
```

`SET_RELAY` accepts relay numbers 1–4. Boolean fields in `SET_LED_STATE` accept `0`/`1`; effect names are `NONE`, `SOLID`, `BREATHING`/`BREATH`, `RAINBOW`, and `AMBIENT`.

## Responses

```text
<BOOT_READY>
<PONG|SEQ=n>
<SYNC_OK|SEQ=n>
<ACK|COMMAND|SEQ=n>
<ACK_SUCCESS|CMD=SET_LED_STATE|SEQ=n|MODE=SOLID>
<ACK_SUCCESS|CMD=SET_LED_STATE|SEQ=n|MODE=SOLID|DUP=1>
<ACK_FAILURE|CMD=SET_LED_STATE|SEQ=n|MODE=SOLID|REASON=INVALID_COLOR>
<ERR|INVALID_PACKET>
```

The ESP8266 sends `<BOOT_READY>` during setup. It echoes a supplied sequence in `PONG`, normal `ACK`, and `SYNC_OK`. LED acknowledgments are correlated with the pending LED sequence; duplicate LED state requests are acknowledged with `DUP=1`.

Errors currently include `INVALID_PACKET`, `PACKET_TOO_LONG`, `QUEUE_FULL`, `UNKNOWN_COMMAND`, `INVALID_ARGUMENT`, `INVALID_SYNC`, `SYNC_TIMEOUT`, and `RUNTIME_STALLED`.

## Synchronization and liveness

The ESP32 starts in `CONNECTING`, sends a ping immediately and then every 2 seconds, and treats the link as timed out after 6500 ms without a liveness response. A boot-ready, pong, or compatible acknowledgment causes the ESP32 to send a full relay sync. A valid `SYNC_OK` transitions the ESP32 to `RUNNING` and causes the LED state to be re-applied.

The ESP8266 runtime transitions `BOOTING → WAITING_FOR_SYNC → SYNCING → RUNNING`. In `RUNNING`, incoming ping/heartbeat/command traffic refreshes its heartbeat timestamp; 5 seconds without it enters `DISCONNECTED`. The watchdog checks every 500 ms, treats sync as stalled after 5 seconds and running as stalled after 10 seconds, clears parser/queue state, sends an error, and returns to `WAITING_FOR_SYNC`.

## LED acknowledgment flow

1. ESP32 derives desired power, brightness, speed, mode, and color from canonical lighting state.
2. It sends `SET_LED_STATE` with a sequence and enters `WAITING_ACK`.
3. ESP8266 validates all required fields and either applies the effect or identifies a duplicate.
4. ESP8266 responds with `ACK_SUCCESS` or `ACK_FAILURE`.
5. ESP32 marks the state synchronized on the matching success sequence. Timeout/failure retries are bounded at three attempts; exhausted retries leave LED status `ERROR`.
